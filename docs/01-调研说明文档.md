## 1. 调研背景与目标

### 1.1 调研背景

3D Gaussian Splatting（3DGS）是 2023 年由 INRIA 团队提出的革命性 3D 场景表示与渲染技术。相较于传统的网格（Mesh）或点云（Point Cloud），3DGS 通过数百万个 3D 高斯核的叠加来表示场景，能在保持高质量渲染的同时实现实时渲染性能。

随着 3DGS 技术的成熟，业界领先的全景漫游引擎 Krpano 在 2025 年 7 月发布的 1.23 版本中正式引入了 3DGS 渲染支持，标志着 3DGS 已从学术研究走向商业应用。

[来源: krpano 官方发布说明 `krpano.com/docu/releasenotes/?version=123`]

### 1.2 调研目标

本调研旨在为构建一款**开源、轻量级、高性能、高可拓展的 Web 端 3DGS 渲染引擎**提供技术决策依据，具体回答以下问题：

1. **数据格式**：3DGS 数据应采用什么格式在 Web 端传输和加载？
2. **渲染引擎**：是否需要自研渲染引擎？现有开源方案是否满足需求？
3. **性能边界**：在不同设备上能达到怎样的渲染性能？
4. **兼容性**：需要覆盖哪些浏览器和设备？回退方案如何？
5. **功能对标**：与 Krpano 相比，核心功能差距在哪里？
6. **技术可行性**：整体方案的可行性如何？关键风险有哪些？

### 1.3 调研方法

- **一手资料**：官方文档、发布说明、GitHub 仓库 README
- **二手资料**：技术博客、学术论文、基准测试报告
- **实证验证**：项目源码审查、API 调用验证、npm 包实际安装测试

## 2. 3DGS 技术原理

### 2.1 基本概念

3DGS 用一组 3D 高斯函数（Gaussian）来表示场景。每个高斯核（称为 Splat）具有以下属性：

| 属性 | 说明 | 训练输出格式 |
|------|------|------------|
| **位置 (Position)** | 高斯核在世界空间中的中心坐标 | float32 × 3 (12B) |
| **缩放 (Scale)** | 高斯核在三个轴向上的大小 | float32 × 3 (12B, log 空间) |
| **旋转 (Rotation)** | 高斯核的朝向（四元数） | float32 × 4 (16B) |
| **颜色 (Color)** | 基础颜色（球谐函数 DC 分量） | float32 × 3 (12B) |
| **球谐高阶 (SH Rest)** | 视角相关颜色变化 | float32 × 45 (180B, SH degree 3) |
| **不透明度 (Opacity)** | 高斯核的透明度 | float32 (4B, sigmoid 前) |
| **法线 (Normal)** | 法线向量（训练后通常不使用） | float32 × 3 (12B) |

### 2.2 标准 PLY 格式

3DGS 训练输出的标准格式为 PLY（Polygon File Format），每个高斯核占 **248 字节**。

```
属性组成 (每 Gaussian):
  x, y, z              12B   位置
  nx, ny, nz           12B   法线 (通常全 0, 冗余)
  f_dc_0..2            12B   球谐 DC 分量 (基础颜色)
  f_rest_0..44        180B   球谐高阶分量 (SH degree 3)
  opacity               4B   不透明度
  scale_0..2           12B   缩放 (log 空间)
  rot_0..3             16B   旋转四元数
  ─────────────────────────
  合计                 248B
```

### 2.3 数据规模参考

| 场景类型 | Gaussian 数量 | 原始 PLY 大小 |
|---------|-------------|-------------|
| 小物体（杯子） | 50K - 200K | 12 - 50 MB |
| 中等场景（房间） | 500K - 1M | 124 - 248 MB |
| 大场景（建筑） | 2M - 5M | 496MB - 1.2GB |
| 超大场景（城市） | 10M+ | 2.5GB+ |

### 2.4 渲染原理

3DGS 渲染流程：

1. **投影**：将每个 3D 高斯核投影到 2D 屏幕空间，形成一个椭圆（2D 高斯）
2. **排序**：按深度从后到前排序所有可见高斯核（Alpha Blending 要求）
3. **光栅化**：为每个高斯核生成一个四边形（Quad），在片段着色器中计算高斯衰减
4. **混合**：使用 Alpha Blending 将所有高斯核叠加到帧缓冲

关键特征：
- 每帧需要对所有可见 Splat 进行排序（计算密集型）
- 排序质量直接影响渲染正确性（透明度混合）
- 片段着色器工作量与像素数量成正比

### 2.5 数据冗余分析

| 属性 | 占比 | 冗余度 | 说明 |
|------|------|--------|------|
| SH 高阶系数 | 72.6% (180/248B) | 高 | 对视觉质量贡献递减，可大幅压缩 |
| 法线字段 | 4.8% (12/248B) | 完全冗余 | 训练后不使用 |
| float32 精度 | — | 过高 | 视觉感知远不需要 float32 精度 |

> **结论**：原始 PLY 格式存在巨大的压缩空间，理论上可达 10-20 倍压缩比而视觉质量几乎无损。

## 3. 数据格式调研

### 3.1 格式对比

| 格式 | 体积/Splat | vs PLY 压缩比 | SH 支持 | LOD | 许可证 | Web 可用 |
|------|-----------|-------------|---------|-----|--------|---------|
| **.ply** (原始) | ~248 B | 基准 (1×) | degree 0-3 | ❌ | 开放 | ❌ 过大 |
| **.sogs** (Fraunhofer HHI) | ~5-12 B | 20-40× | degree 0-3 | ❌ | 学术 | ❌ 仅离线 |
| **.spz v4** (Niantic) | ~28 B | ~10× | degree 0-4 | ❌ | **MIT** | ✅ WASM |
| **.splat** | ~32 B | ~7× | ❌ 无 SH | ❌ | MIT | ✅ 原生 |
| **.ksplat L2** | ~94 B | ~2.6× | degree 0-2 | 基础 | MIT | ✅ JS |
| **.ksplat L1** | ~124 B | ~2× | degree 0-2 | 基础 | MIT | ✅ JS |
| **.sog** (PlayCanvas) | ~12-16 B | 15-20× | degree 0-3 | ✅ 流式 | MIT | ✅ |

[来源: SPZ README `github.com/nianticlabs/spz`；PlayCanvas 博客 `blog.playcanvas.com`；gsplat 基准测试]

### 3.2 SPZ 格式深度分析

SPZ 是 Niantic Labs 开源的 3DGS 压缩格式，是当前 Web 端运行时的**最优选择**。

**核心特性**：
- **ZSTD 压缩**：高压缩比 + 快速解压
- **独立属性流**：位置、旋转、缩放、颜色、SH 分别独立压缩，支持并行解压
- **SH 0-4 支持**：完整球谐函数支持，可配置量化精度
- **WASM 绑定**：提供 WebAssembly 解码器，高性能
- **MIT 许可证**：商业友好

**量化参数**：

| 参数 | 默认值 | 范围 | 说明 |
|------|--------|------|------|
| `shDegree` | 1 | 0-4 | 球谐函数阶数 |
| `sh1Bits` | 5 | 1-8 | SH degree 1 量化位数 |
| `shRestBits` | 4 | 1-8 | SH degree 2+ 量化位数 |

**量化代价参考**：

| SH Degree | 体积/Splat | 1M Splats | 画质影响 | 推荐场景 |
|-----------|-----------|-----------|---------|---------|
| SH 0 | ~22 B | ~22 MB | 失去视角相关颜色 | 移动端极致 |
| SH 1 | ~28 B | ~28 MB | 几乎无损 | **推荐默认** |
| SH 2 | ~48 B | ~48 MB | ~1.2 dB 损失 | 桌面端高质量 |
| SH 3 | ~75 B | ~75 MB | ~1.5 dB 损失 | 桌面端极致 |

[来源: SPZ README `github.com/nianticlabs/spz`；gsplat 基准测试]

### 3.3 SOG 格式（流式 LOD）

SOG（Spatially Ordered Gaussians）是 PlayCanvas 开发的格式，专为流式加载和 LOD 设计。

**核心特性**：
- 空间排序（Morton Code / Z-order）
- 分块流式加载
- 内置 LOD 层级
- 适合超大场景（>5M splats）

[来源: PlayCanvas 博客 — SOG 流式 LOD]

### 3.4 格式选型建议

| 场景规模 | 推荐格式 | 理由 |
|---------|---------|------|
| < 500K splats | .spz (SH 1) | 单文件，快速加载，~14 MB |
| 500K - 5M splats | .spz (SH 1) | 平衡质量与体积，~28-140 MB |
| > 5M splats | .sog (流式 LOD) | 分块流式加载，渐进式渲染 |

**核心结论**：
- **SPZ 为推荐首选运行时格式**——MIT 开源、10× 压缩、WASM 解码、SH 0-4 支持
- **SOG 用于超大场景流式加载**——分块 LOD，渐进式渲染
- **多格式兼容**——不应人为限制为单一格式，应支持 .spz / .splat / .ply / .sog

## 4. 渲染引擎生态调研

### 4.1 开源引擎对比

| 引擎 | Stars | 核心 API | 排序策略 | LOD | 性能标杆 | 许可证 |
|------|-------|---------|---------|-----|---------|--------|
| **SuperSplat** | 9.7k | WebGPU+WebGL2 | GPU Radix (WGSL) | ✅ Streaming (SOG) | 76fps @ 35M | MIT |
| **Spark** | — | WebGL2 (Three.js) | CPU Bucket Sort (Worker) | ✅ 5 格式 | 60fps @ 1-5M | MIT |
| **GaussianSplats3D** | ~1.5k | WebGL2 (Three.js) | CPU Worker | .ksplat 基础 | 30-60fps @ 1M | MIT |
| **antimatter15/splat** | 3k | WebGL2 | CPU (~4fps) | ❌ | 极简原型 | MIT (归档) |
| **Luma Web** | — | WebGL2 (Three.js) | CPU | ❌ | 快速嵌入 | MIT |
| **WebSplatter** | 学术 | WebGPU | Wait-free Sort | ❌ | 33fps @ 6.1M | 论文 |

[来源: GitHub 仓库数据；PlayCanvas 博客；Spark npm 包 `@sparkjsdev/spark@2.1.0` README]

### 4.2 SuperSplat 深度分析

**定位**：完整 PWA 编辑器 + PlayCanvas Engine 组件

**核心优势**：
- **WebGPU GPU Radix Sort**（WGSL Compute Shader），PackedSplats 16B/splat
- 35M splats 场景下 75.8fps（M4 Max 桌面端）
- WebGPU 比 WebGL2 快 5.7×（35M splats 场景）
- 完整格式支持：.ply / .sog / .spz / .splat / .ksplat
- SOG 流式 LOD 支持

**局限**：
- 基于 PlayCanvas Engine（非 Three.js 生态）
- 集成复杂度高（PWA 编辑器架构）
- Vue/React 集成不友好

[来源: PlayCanvas 博客 `blog.playcanvas.com/new-in-supersplat-webgpu-and-streaming-bring-huge-performance-wins`；GitHub `github.com/playcanvas/supersplat`]

### 4.3 Spark 深度分析

**定位**：Three.js 3DGS 渲染库（npm 包 `@sparkjsdev/spark`），由 World Labs 开发

**核心优势**：
- **原生 Three.js 集成**：`new SparkRenderer({ renderer })`，3 行代码集成
- **5 格式支持**：sogs / spz / ksplat / ply / splat
- **dyno shader graph**：可在 GPU 上动态创建/编辑 splat 效果
- **CPU Worker 排序**：Rust/WASM 编译，不阻塞主线程
- 移动端 1-3M splats 流畅

**API 示例**：
```typescript
import * as THREE from 'three';
import { SparkRenderer, SplatMesh } from '@sparkjsdev/spark';

const renderer = new THREE.WebGLRenderer({ antialias: true });
const spark = new SparkRenderer({ renderer });
scene.add(spark);

const splat = new SplatMesh({ url: '/scene.spz' });
scene.add(splat);
```

**局限**：
- 仅 WebGL2（目标 98%+ 兼容性），无 WebGPU 路径
- 构建依赖 Rust 工具链（WASM 编译）
- CPU 排序在大场景（>10M）时性能不如 GPU 排序
- Worker 通信有 ~1-2 帧延迟

[来源: Spark npm 包 `@sparkjsdev/spark@2.1.0` README 及 package.json]

### 4.4 SuperSplat vs Spark 对比

| 维度 | SuperSplat | Spark |
|------|-----------|-------|
| 架构定位 | PWA 编辑器 + PlayCanvas 组件 | Three.js 渲染库 (npm) |
| 渲染管线 | WebGPU GPU Radix Sort | CPU Bucket Sort (WASM Worker) |
| 最大 splat | ~1.35M (WebGPU), ~10M (WebGL2) | ~5-20M (桌面), 1-3M (iPhone) |
| Three.js 集成 | 间接（PlayCanvas Engine） | 原生 |
| Vue/React 集成 | 不友好 | 友好 |
| 可编程性 | GSplatContainer API | dyno shader graph |
| 排序延迟 | GPU 同步, <1 帧 | Worker 通信 ~1-2 帧 |
| 移动端 | WebGPU ~2× WebGL2 | 1-3M splats 流畅 |
| 开发者门槛 | 高 | 低 |

**选型建议**：
- **场景 >10M + 追求极致性能** → SuperSplat（WebGPU GPU 排序）
- **场景 <5M + Three.js 生态 + 需要定制** → Spark（dyno shader, npm 安装）
- **混合策略** → Phase 1 用 Spark 快速落地，Phase 2 评估 SuperSplat 核心

### 4.5 自研渲染引擎评估

| 维度 | 自研 | 复用开源 |
|------|------|---------|
| 开发周期 | 6-12 个月 | 2-4 周集成 |
| 性能上限 | 理论最高 | SuperSplat 76fps@35M 已足够 |
| 维护成本 | 高 | 低（社区维护） |
| 定制灵活性 | 100% | 70-90% (Fork 后) |
| 风险 | 高（大概率不如 SuperSplat） | 低 |

> **核心结论**：不自研渲染引擎。SuperSplat（76fps@35M）和 Spark（60fps@1-5M）的性能已远超业务需求。自研的投入产出比极低，大概率不如现有开源方案。**核心差异化应在于漫游框架（场景图、热点系统、配置格式、交互体验），而非渲染引擎本身。**

## 5. 竞品分析：Krpano 1.23

### 5.3 Krpano 的核心价值

Krpano 被选择不是因为渲染性能，而是因为：

1. **多场景漫游**：场景图 + 热点链接 + 过渡动画

3. **配置驱动**：XML 编辑（非代码），业务人员可操作
4. **UI 框架**：菜单、导航、标注、缩略图
5. **触控体验**：手势、惯性、自动旋转、陀螺仪
6. **作者工具链**：MAKE VTOUR（droplet）一键生成

### 5.5 超越策略

## 6. 浏览器兼容性调研

### 6.1 兼容性矩阵

| 浏览器 | WebGL2 | WebGPU | 市场份额 | 备注 |
|--------|--------|--------|---------|------|
| Chrome 113+ | ✅ | ✅ | ~65% | 完整支持 |
| Edge 113+ | ✅ | ✅ | ~5% | 完整支持 |
| Firefox | ✅ | ⚠️ 有限 | ~3% | WebGPU 仅 Nightly |
| Safari (iOS < 18) | ✅ | ❌ | ~15% | 需 WebGL2 回退 |
| Safari (iOS 18+) | ✅ | ⚠️ 实验性 | ~8% | 默认关闭 |
| Safari (macOS 15+) | ✅ | ⚠️ 实验性 | ~3% | 默认关闭 |

[来源: PlayCanvas 博客引用 caniuse 数据，WebGPU 覆盖率约 85%（2026-06）]

### 6.2 关键结论

> **WebGL2 回退是必需品而非可选项。** iOS Safari（占移动端 ~27% 份额）在 iOS 18+ 之前完全不支持 WebGPU。必须提供完整的 WebGL2-first 方案。

### 6.3 SharedArrayBuffer 要求

Spark 使用 Rust/WASM Worker 执行 splat 排序，需要 `SharedArrayBuffer` 进行高效 Worker 通信。启用 `SharedArrayBuffer` 需要配置跨域隔离头：

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

**影响**：未配置时，Worker 通信退化为 `postMessage` 结构化克隆，1M splats 排序从 ~5ms 退化为 ~150ms，帧率从 60fps 降至 ~7fps。

[来源: MDN Web Docs — SharedArrayBuffer 安全要求]

### 7.2 Spark 性能数据

| 场景规模 | 帧率 | 测试环境 |
|---------|------|---------|
| 1-5M splats | 60fps | 桌面端 |
| 1-3M splats | 流畅 | iPhone |

[来源: Spark 官方文档 `sparkjs.dev`]

### 7.3 帧时间预算分析（1M splats，桌面端 60fps = 16.6ms）

```
阶段                    WebGPU 管线      WebGL2 管线 (优化后)
─────────────────────────────────────────────────────────
视锥体剔除              0.3ms (GPU)      1.5ms (WASM)
深度计算                0.2ms (GPU)      1.0ms (WASM)
排序                    1.5ms (GPU)      4.0ms (WASM Worker)
数据上传/绑定           0.1ms (零拷贝)   1.0ms (bufferData)
顶点着色 (投影)         2.5ms            3.0ms
片段着色 (光栅化)        4.0ms            5.0ms
混合 (blending)         1.5ms            2.0ms
后处理                  0.5ms            0.5ms
─────────────────────────────────────────────────────────
总计                    ~10.6ms ✅       ~18.0ms ⚠️
```

### 7.4 常见性能陷阱

| 陷阱 | 影响 | 根因 |
|------|------|------|
| 像素比过高 (DPR=2) | 片段着色器 4× 开销 | Retina 屏以 2× 分辨率渲染 |
| MSAA 抗锯齿开启 | GPU 开销 3× | 3DGS 的 alpha blending 不需要 MSAA |
| 缺少 COOP/COEP 头 | 排序 10-30× 退化 | SharedArrayBuffer 不可用 |
| 双 RAF 循环 | 每帧额外 1-2ms | 两个独立 requestAnimationFrame |
| 全量加载 | 首屏慢、内存高 | 无 LOD 流式加载 |

## 10. 调研结论与建议

### 10.1 核心结论

1. **不自研渲染引擎**：SuperSplat（76fps@35M）和 Spark（60fps@1-5M）的性能已远超需求。自研投入产出比极低。

2. **渲染后端策略**：Spark (WebGL2/Three.js) 为主 + SuperSplat 引擎核心 (WebGPU) 渐进增强。Spark 集成快（3 行代码），SuperSplat 性能强（5.7× 加速）。

3. **运行时格式**：SPZ 为推荐首选（MIT, 10× 压缩, WASM, SH 0-4），SOG 用于超大场景流式 LOD。支持多格式，不人为限制。

4. **WebGL2 回退必需**：iOS Safari 占移动端 ~27%，WebGPU 覆盖率仅 85%。必须提供完整 WebGL2-first 方案。

5. **核心差异化在漫游框架**：SceneGraph + HotspotSystem + TourConfig + PluginSystem 是对标 Krpano 的核心价值，而非渲染引擎本身。

6. **性能关键配置**：COOP/COEP 头（SharedArrayBuffer）、像素比 1.0（非 DPR）、关闭 MSAA、单一 RAF 循环。

### 10.2 技术选型建议

| 模块 | 策略 | 方案 |
|------|------|------|
| 渲染引擎 | 复用开源，双层抽象 | Spark (WebGL2) 为主 + SuperSplat (WebGPU) 渐进增强 |
| 运行时格式 | 多格式支持，SPZ 首选 | SPZ + .splat + .ply + SOG |
| 数据转换 | 独立 CLI 工具 | splat-transform + SPZ 工具链 |
| 漫游框架 | 自研，核心差异化 | SceneGraph + Hotspot + TourConfig + Plugin |
| 配置格式 | 自研 | tour.json（声明式 JSON，类比 krpano XML） |
| 组件封装 | 自研薄适配层 | React / Vue 组件 |

### 10.3 关键风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| COOP/COEP 部署限制 | SharedArrayBuffer 不可用 | 中 | 提供非 SAB 降级路径 |
| iOS Safari WebGPU 延迟 | 移动端无法用 GPU 排序 | 高 | WebGL2 + WASM Worker 保底 |
| Spark 维护中断 | 依赖断裂 | 低 | Fork 并维护内部版本 |
| 超大场景内存溢出 | 移动端崩溃 | 中 | LOD Streaming + 设备预算表 |
| SPZ WASM 加载延迟 | 首屏加载慢 | 中 | 分块加载 + 渐进式解码 |
