# 数据转换能力实测评估与优化方案

调研日期：2026-09-15

调研对象：`packages/convert` 的数据转换链路，包括 PLY 解析、SPLAT/SPZ/SOG/压缩 PLY 读写、CLI、batch、质量回归测试，以及 `renderer-three` 的 SOG v3 消费端。

结论先行：当前转换包已经具备完整的格式覆盖、192 项 convert 单测、743 项全仓单测、lint 和 typecheck 全部通过；但真实实测仍发现两类高风险正确性问题（PLY 快路径在合法布局下静默错读、CRLF 头部偏移错误），以及 batch 输出覆盖、SH 跨格式丢失、CLI 仍走 AoS 高内存路径等多项需治理的问题。

## 3. 问题清单

### 3.1 P0：合法 PLY 布局下快路径静默错读

涉及文件：[ply-parser.ts](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/ply-parser.ts:369)

根因：`tryFastPathParsePly` 直接使用 `new DataView(buffer, headerEnd)` 作为 vertex 数据起点（[ply-parser.ts:443](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/ply-parser.ts:443)），没有计算 `vertex` element 在文件体中的真实偏移。只要 `vertex` 前面存在 `face`、`chunk` 或其他 element，快路径就会把前面 element 的字节当作 vertex 属性读取。

实测构造：

```text
element face 1
property list uchar int vertex_indices
element vertex 1
property float x
property float y
property float z
```

慢路径正确读出 `{ x: 1, y: 2, z: 3 }`；`loadGaussiansFromPly` 和 `loadGaussiansFromPlySoA` 都静默返回接近 0 的错误位置，不抛异常。PLY 规范允许 element 按任意顺序声明，因此这是兼容性缺陷，不只是理论边界。

修复方向：

1. 在 `tryFastPathParsePly` 中计算 vertex 起始偏移：`headerEnd + sum(header.elements 中位于 vertex 之前的 count * stride)`。
2. 校验计算后的 vertex 数据区不越界，越界时回退慢路径抛出明确错误。
3. 新增回归测试：`face` 在 `vertex` 前的 PLY 必须与慢路径结果一致。

### 3.2 P0：CRLF PLY 头部解析偏移错误

涉及文件：[ply-parser.ts:103](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/ply-parser.ts:103)

根因：`parsePlyHeader` 使用 `offset += line.length + 1`（[ply-parser.ts:125](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/ply-parser.ts:125)）推进偏移。对 `\n` 正确，对 `\r\n` 只跳过一个终止字节，导致 `headerEnd` 少 1 字节；随后二进制 body 整体错位。

实测：CRLF 二进制 PLY 的第一顶点应为 `(1, 2, 3)`，`parsePlyHeader` 返回 `headerEnd: 121`，实际正确偏移是 122；`parsePly`/`loadGaussiansFromPly` 最终读出接近 0 的错误位置。

修复方向：

1. `readLine` 返回 `nextOffset`，或调用方在遇到 `\r\n` 时额外跳过 `\r`。
2. 增加 CRLF 回归测试，覆盖 header 内每行和 `end_header\r\n`。
3. 保持 ASCII PLY 的 CRLF 兼容，并在解析后校验 body 起始处属性不再错位。

### 3.3 P1：batch 输出路径碰撞导致文件互相覆盖

涉及文件：[cli.ts:531](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:531)

根因：batch 用 `file.replace(/\.(ply|splat|spz|sog)$/i, \`.\\${format}\`)` 生成输出名（[cli.ts:561](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:561)）。同目录存在 `bench-1000.ply`、`bench-1000.splat`、`bench-1000.spz` 时，三个文件都映射到 `bench-1000.spz`，后处理覆盖先处理结果，manifest 仍记录三条虚构的成功记录。

实测：一个目录含 `bench-1000.ply/.splat/.spz`，batch 输出到新目录后只保留其中一个文件，manifest 中 3 个 `files[].output` 全指向同一路径。

修复方向：

1. 输出名保留源扩展信息，例如 `基准名.<输入扩展>.<目标扩展>`；或先检测碰撞，碰撞时追加 `-1/-2` 唯一后缀。
2. manifest 写入前检查输出路径唯一性，重复时直接判定失败或自动重命名。
3. 新增同样 base 名、不同源格式的 batch 回归测试。

### 3.4 P1：压缩 PLY 写入端丢失 SH，且文档声称 SH 已保存

涉及文件：[compressed-ply-writer.ts:73](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/compressed-ply-writer.ts:73)

根因：`writeCompressedPlySoA` 的 header 只声明 `packed_position/packed_rotation/packed_scale/packed_color` 和 chunk 范围属性（[compressed-ply-writer.ts:80](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/compressed-ply-writer.ts:80)），没有写任何 SH 数据；读取端 `loadSuperSplatPly` 和 `loadSuperSplatFastPath` 也都把 `shDegree` 固定为 0。

实测：SH degree 1 的合成 PLY 经 `to-compressed-ply` 后，再读取压缩 PLY 得到 `shDegree=0`、`sh` 不存在。这与 [c06-format-adaptation-research.md](/Users/sacrtap/Documents/project_work/3dgs/docs/Technical-Debt/c06-format-adaptation-research.md:40) 中“C-05 已含 SH 量化”的表述不一致。

修复方向：

1. 短期先把文档改为真实表述：压缩 PLY 当前只保留 base attributes，不保留 SH。
2. 若继续宣称 SuperSplat 兼容且保留 SH，需要定义 optional `element sh` 布局，并在 writer/reader 两侧同步实现和 round-trip 测试。
3. CLI 打印 `to-compressed-ply` 结果时增加 SH 损失提示，避免用户在转换后才通过 `info` 发现。

### 3.5 P1：SOG v3 → SPZ/SOG → SPLAT 批量转换丢失 SH

涉及文件：[cli.ts:399](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:399)

根因：`decodeSogToCloud` 只解码 chunk 内的 base attributes，显式返回 `shDegree: 0`（[cli.ts:500](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:500)）。batch 的 SOG 输入分支直接使用该函数（[cli.ts:590](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:590)），完全没有读取 SOG v3 文件尾部的 SH overlay。

实测：源 PLY `shDegree=1` → SOG v3（overlay 长度 9,000）→ batch 转 SPZ，输出 SPZ 的 `shDegree=0`、`sh` 不存在。

修复方向：

1. batch 的 SOG 分支先 `parseSogMetadata`，若 `shOverlayOffset/shOverlaySize` 存在，用 `readShOverlaySoA` 恢复 SH。
2. 将 `decodeSogToCloud` 内部数据改为先构造 SoA 或直接在 AoS 上注入 `sh`，避免再经过一次有损转换。
3. 增加 SOG v3 → SPZ round-trip 测试，断言 SH degree 和量化误差。

### 3.6 P1：CLI 主流程仍走 AoS，SoA 收益没有进入转换命令

涉及文件：[cli.ts:251](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:251)、[sog-writer.ts:286](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/sog-writer.ts:286)

根因：CLI 用 `loadGaussiansFromPly`、`loadGaussiansFromSplat` 等 AoS API 构造 `GaussianCloud`，随后 `writeSog/writeSplat/writeSpz` 内部再 `toSoA`。虽然写入端已 SoA 化，CLI 仍会生成大量 JS 对象并额外拷贝。

实测影响：200k 场景下 CLI 等价 AoS 路径堆增量 +150 MB、RSS +242 MB，比 SoA 路径（+13 MB / +46 MB）高约 10 倍和 5 倍；500k 场景 AoS 解析本身堆增量 +311 MB，是当前大文件 OOM 风险的主要来源。

修复方向：

1. CLI 所有加载入口切换到 `loadGaussiansFromPlySoA`、`loadGaussiansFromSplatSoA`、`loadGaussiansFromSpzSoA`。
2. 补 `pruneGaussiansSoA` 和对应 quickselect 路径，让 `--prune`/`--max-splats` 不再经过 AoS 对象数组。
3. `convertCloud` 改为消费 `GaussianCloudSoA`，写入端直接调用 `writeSplatSoA/writeSpzSoA/writeSogSoA/writeCompressedPlySoA`。
4. 用 500k 合成 PLY 增加 CLI 内存冒烟，验收目标为常规堆上限内完成，且与 AoS 结果 byte 级一致。

### 3.7 P2：`info .spz` 不显示 splat 数和 SH 阶数

涉及文件：[cli.ts:762](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:762)

现状：`.spz` 分支只打印“解压后可查看详细信息”（[cli.ts:779](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:779)），而 SPZ 头部只有 16 字节，解压成本很低，`parseSpzHeader` 已经可用。

修复方向：`showInfo` 对 SPZ 调用 `parseSpzHeader`，输出 `numPoints`、`shDegree`、`version`、`fractionalBits`、容器类型；CLI 允许异步后改为 `await`。

### 3.8 P2：SOG v3 的 `shMode` 字段存在双语义

涉及文件：[sog-writer.ts:466](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/sog-writer.ts:466)、[sog-writer.ts:499](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/sog-writer.ts:499)

现状：`--sog-version 3 --sh-mode 1` 会在主 header 写入 `shMode=1`，同时 overlay header 写入 `2`（full SH overlay），chunk 尾部又追加 3B DC。`parseSogMetadata` 返回主 header 的 `shMode=1`，调用端无法直接判断完整 overlay 是否存在。

修复方向：把“chunk 内 SH DC 追加”和“v3 overlay”拆成独立协议字段，或 v3 且存在 overlay 时主 header `shMode` 写 `2`；同步更新 `sog-streamer` 的字段解释和测试。

### 3.9 P2：CLI 版本号与包版本号不一致

涉及文件：[cli.ts:56](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:56)

现状：`3dgs-convert --version` 输出 `0.1.0`，`packages/convert/package.json` 版本是 `0.4.0`。发布后用户无法从 CLI 判断实际版本。

修复方向：从包版本读取版本号，或至少改为同一常量，并加 CLI 冒烟断言。

### 3.10 P2：包级 Node engines 与根政策不一致

涉及文件：[package.json](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/package.json:46)

现状：根 `package.json` 是唯一权威声明 `node >=22`，但所有发布包仍声明 `>=18`。`CompressionStream` 等 API 在 Node 18 可用，但仓库实际 CI 和运行基线已经是 Node 22+，包声明会造成外部用户错误预期。

修复方向：发布包 engines 统一为 `>=22`；在 workflow 中不引入低于该版本的新 Node。

### 3.11 P2：SPZ writer 函数注释与真实布局相反

涉及文件：[spz-writer.ts:62](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/spz-writer.ts:62)

现状：顶部文件注释和测试都确认“整文件 gzip”，但 `writeSpz` 的 JSDoc 仍写“Header 未压缩 + Body gzip”（[spz-writer.ts:65](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/spz-writer.ts:65)），会让后续维护者再次引入 M5 一类布局错误。

修复方向：JSDoc 改成“整个文件为单个 gzip 流，解压后是 16B header + body”，并删除“仅压缩 body”的历史注释。

### 3.12 P2：tour 生成仍是硬编码热点，且 `--title` 未声明

涉及文件：[cli.ts:653](/Users/sacrtap/Documents/project_work/3dgs/packages/convert/src/cli.ts:653)

### 3.13 P2：全量 coverage 门禁当前不可用
