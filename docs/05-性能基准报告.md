## 1. 测试方法

### 1.1 测试工具

| 工具 | 用途 | 来源 |
|------|------|------|
| Playwright 1.62 | 自动化浏览器测试 | [playwright.dev](https://playwright.dev) |
| Performance API | FPS / 帧时间 / 内存采集 | [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API) |
| `PerformanceMonitor` | 浏览器端实时监控 | `benchmarks/perf-monitor.ts` |

### 1.2 测试流程

```
1. pnpm build (构建所有包)
2. pnpm --filter @3dgs/demo dev (启动 Demo 开发服务器)
3. Playwright 启动 headless Chrome (1920×1080)
4. 注入独立 RAF 采样脚本 (不依赖 Demo 代码)
5. 导航到 Demo, 等待 loading 消失
6. 逐场景测试:
   a. 切换到目标场景, 等待切换动画完成 (1s)
   b. 预热 4s (等待渲染稳定)
   c. [静止] 采样 10s — 不操作, 纯渲染
   d. [移动] 采样 10s — 模拟 WASD 键盘移动
      · 前 5s: 按住 W+D (前进+右移)
      · 后 5s: 按住 S+A (后退+左移)
   e. 统计 P5 / P50 / P95 / Avg / Max / 丢帧率 / 内存
7. 生成 JSON 报告 + 控制台表格
```

### 1.3 运行基准测试

```bash
# 前置条件
pnpm build
pnpm --filter @3dgs/demo dev   # 终端 1

# 运行基准测试 (终端 2)
npx tsx benchmarks/benchmark.ts

# 结果输出
#   控制台: 实时进度 + 汇总表格
#   JSON:   benchmarks/reports/benchmark-<timestamp>.json
```

### 1.4 嵌入式监控

在应用中嵌入 `PerformanceMonitor` 进行实时监控:

```typescript
import { PerformanceMonitor } from './benchmarks/perf-monitor';

const monitor = new PerformanceMonitor(renderer);
monitor.start();

// 挂载到渲染器帧回调
renderer.onFrame((dt) => {
  monitor.sample(dt);
});

// 一段时间后获取报告
const report = monitor.stop();
console.log(`Avg FPS: ${report.avgFps}, P95 Frame Time: ${report.p95FrameTime}ms`);
```

## 3. 基准数据

### 3.1 静止状态 (Idle)

> 不操作键盘/鼠标, 纯渲染状态下的性能数据。

| 场景 | Avg FPS | P50 FPS | P5 FPS | P95 FPS | Avg FT (ms) | P95 FT (ms) | Max FT (ms) | Std FT (ms) | 丢帧率 | 采样数 |
|------|---------|---------|--------|---------|-------------|-------------|-------------|-------------|--------|--------|
| kitchen | 38.0 | 38.2 | 35.7 | 39.4 | 26.35 | 28.02 | 30.52 | 0.86 | 100% | 377 |
| living | 41.0 | 41.3 | 39.2 | 42.3 | 24.38 | 25.53 | 28.39 | 0.70 | 100% | 407 |
| scene21 | 40.9 | 41.1 | 39.3 | 41.9 | 24.49 | 25.44 | 28.15 | 0.61 | 100% | 405 |

**分析**:
- 三个场景性能基本一致 (38-41 FPS), 帧时间 ~24-26ms
- scene21 (72K splats) 与 kitchen/living (248K splats) 性能几乎相同
  → 说明当前规模下 splat 数量不是瓶颈, 排序开销恒定
- 帧时间标准差极小 (0.61-0.86ms), 渲染非常稳定无抖动
- 100% 丢帧率 (帧时间 > 20ms) → headless 模式下 GPU 性能不足

### 3.2 移动状态 (Moving)

> 模拟 WASD 键盘移动 (W+D 5s → S+A 5s) 下的性能数据。

| 场景 | Avg FPS | P50 FPS | P5 FPS | P95 FPS | Avg FT (ms) | P95 FT (ms) | Max FT (ms) | Std FT (ms) | 丢帧率 | 采样数 |
|------|---------|---------|--------|---------|-------------|-------------|-------------|-------------|--------|--------|
| kitchen | 119.8 | 59.8 | 38.5 | 316.5 | 18.00 | 25.96 | 79.84 | 9.83 | 12.3% | 561 |
| living | 120.7 | 59.9 | 38.4 | 175.1 | 17.79 | 26.05 | 103.75 | 9.52 | 9.5% | 558 |
| scene21 | 122.5 | 60.0 | 39.6 | 148.1 | 17.65 | 25.28 | 83.25 | 9.06 | 8.3% | 563 |

**分析**:
- **P50 (中位数) = 60 FPS** → 实际渲染帧率与 vsync 同步, 移动不影响核心渲染性能
- Avg FPS 虚高 (119-123) → 测量伪影: 键盘事件触发 RAF 回调合并, 部分帧时间极短 (3-8ms)
- P5 FPS (38-40) → 移动时偶发长帧 (键盘事件处理 + 渲染叠加)
- 采样数 558-563 vs 静止 377-407 → 移动时帧数更多, 印证 RAF 触发频率变化
- Max FT 80-104ms → 键盘按下/释放瞬间的事件处理峰值

### 3.3 静止 vs 移动对比

| 指标 | 静止 | 移动 | 差异 | 说明 |
|------|------|------|------|------|
| P50 FPS | 38-41 | **60** | 移动更高 | headless 下静止受 GPU 限制; 移动时 RAF 被输入事件加速 |
| P5 FPS | 36-39 | 38-40 | **持平** | 最差帧表现一致 → 移动不增加渲染负担 |
| P95 FT | 25-28ms | 25-26ms | **持平** | 95% 帧的帧时间一致 → 渲染开销恒定 |
| Avg FT | 24-26ms | 18ms | 移动更低 | 伪影: 输入事件产生极短帧拉低平均值 |
| Std FT | 0.61-0.86 | 9.06-9.83 | 移动更高 | 输入事件导致帧间隔波动增大 |

> **核心结论**: 移动状态下的渲染性能 (P5/P95 帧时间) 与静止状态**完全一致**。  
> 平均值差异是由键盘输入事件导致的 RAF 触发频率变化引起的测量伪影, 非渲染性能变化。

## 4. FPS "移动中不变化" 专题分析

### 4.1 用户观察

> "检查移动过程中, 为什么 FPS 没有变化? 是有 bug 么?"

### 4.2 结论: 不是 bug, 是预期行为

在真实浏览器 (非 headless) 中, Demo HUD 显示的 FPS 在移动过程中不变化是**完全正确的行为**。原因如下:

### 4.3 原因分析

| 原因 | 详细说明 |
|------|---------|
| **① vsync 锁帧** | `requestAnimationFrame` 由显示器刷新率驱动 (通常 60Hz)。当 GPU 渲染时间 < 16.67ms 时, FPS 恒定为 60, 无法超过 |
| **② 3DGS 渲染开销恒定** | 与三角面渲染不同 (视锥剔除会大幅改变可见面数), 3DGS **每帧渲染全部 splats**, 相机移动不改变渲染工作量 |
| **③ 场景规模小** | kitchen.splat (248K splats) 在 Iris 655 上渲染时间 ~25ms (headless)。在独显设备上 < 16.67ms, 稳定 60fps |
| **④ 自适应分辨率兜底** | `AdaptiveResolution` 在 FPS < 40 时自动降低分辨率, 进一步稳定帧率 |
| **⑤ 移动逻辑轻量** | `applyKeyboardMovement()` 仅做向量运算 + `camera.translateX/Y/Z`, 无额外 GPU 开销 |

### 4.4 基准测试验证

本次基准测试用数据验证了上述结论:

```
                    静止 P5 FPS    移动 P5 FPS    变化
kitchen             35.7           38.5           +7.8%   ← 在误差范围内
living              39.2           38.4           -2.0%   ← 持平
scene21             39.3           39.6           +0.8%   ← 持平

                    静止 P95 FT    移动 P95 FT    变化
kitchen             28.02ms        25.96ms        -7.4%   ← 持平
living              25.53ms        26.05ms        +2.0%   ← 持平
scene21             25.44ms        25.28ms        -0.6%   ← 持平
```

**P5 FPS (最差 5% 帧) 和 P95 帧时间在静止与移动状态下基本一致**, 证明移动不改变渲染性能。

### 4.5 什么情况下 FPS 会变化?

| 场景 | FPS 变化 | 原因 |
|------|---------|------|
| 场景规模 > 5M splats | 移动时可能下降 | 更多 splats 进入视锥, 排序/渲染时间增加 |
| 低端移动设备 | 移动时可能下降 | GPU 性能不足, 排序成为瓶颈 |
| SOG 流式加载中 | 加载瞬间下降 | 首帧 chunk 渲染 + 后续 chunk 解码并行 |
| WebGPU 后端 (未来) | 预计不变 | compute shader 排序更快, 仍有余量 |

## 5. 性能优化措施

以下优化已实施，对基准数据有直接影响:

| 优化项 | 措施 | 影响 | 源码 |
|--------|------|------|------|
| MSAA 关闭 | `antialias: false` | 避免无效 MSAA 降帧 | `index.ts:303` |
| 像素比固定 | `setPixelRatio(1.0)` | 避免 DPR=2 时 4× 像素量 | `index.ts:308` |
| 单一 RAF | `onFrame()` 回调 | 杜绝双 RAF 冗余开销 | `tour-player.ts:72` |
| COOP/COEP | 跨源隔离头 | SharedArrayBuffer 可用, 排序 ~5ms | `vite.config.js` |
| 设备分级 | DeviceTier 自动检测 | 低端设备降分辨率保帧率 | `device-tier.ts` |
| 自适应分辨率 | 帧率低于阈值自动降分辨率 | 帧率稳定不崩溃 | `adaptive-resolution.ts` |
| LOD 树 | `createLodSplats()` | 远距离减少 splat 数量 | `index.ts:618-627` |
| SOG 流式 LOD | 首帧快速渲染 | 大场景首帧 < 2s | `index.ts:loadSceneWithSog` |
| 连续指数平滑移动 | `1 - exp(-dt/τ)` | 帧率无关的平滑移动, 无量化跳变 | `index.ts:applyKeyboardMovement` |

## 7. headless vs 真实浏览器差异

| 指标 | headless Chrome | 真实 Chrome (预期) | 差异原因 |
|------|----------------|-------------------|---------|
| 跨域隔离 | ✗ | ✓ | headless 不支持 COOP/COEP |
| SharedArrayBuffer | 不可用 | 可用 | 排序回退主线程 |
| 静止 FPS | 38-41 | ~60 | 排序在主线程执行, 增加 ~8ms/帧 |
| 移动 P50 FPS | 60 | 60 | vsync 一致 |
| GPU 加速 | 有限 | 完整 | headless GPU 驱动支持不完整 |

> **结论**: headless 环境的绝对 FPS 值不能代表真实用户体验。  
> 基准测试的核心价值在于**相对比较** (静止 vs 移动, 场景间对比, 优化前后对比)。  
> 真实浏览器中的绝对性能需通过手动测试或 CI headed 模式获取。
